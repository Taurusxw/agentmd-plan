# AGENTS.md

> 全局 Codex 工作规则。
> 版本：28.1.0
> 定版日期：2026-08-03
> 目标：用精简、始终在场的纲要约束所有任务；详细执行规则由 `seer-codex-rules` 按需加载，兼顾全面遵守、低 token、低等待和可验证性。

---

# 1. 核心原则

1. 先理解和查证，再判断或修改。
2. 优先沿用项目现有架构、目录、命名、工具和文档体系。
3. 改动保持小而完整，不做无关重构或机械留痕。
4. 所有持久改动必须可复查、可验证、可回溯、可交接。
5. 任务按风险和规模分级，短任务轻量闭环，长任务完整留痕。
6. 避免单文件多职责、重复规则、同义文档和浅层抽象。
7. 保留用户已有修改，不擅自覆盖、回滚、删除或迁移。
8. 回答、解释、审查、诊断或计划请求默认只读；修改、构建、修复或优化请求已授权目标范围内的本地读取、编辑和非破坏性验证，无需再次确认。仅外部写入或发布、破坏性或不可逆操作、付费、凭据披露或实质扩张范围时确认；同一授权范围只确认一次，运行时安全边界仍由 sandbox、approval、permissions、hooks 或 CI 执行。
9. 验收用于证明当前目标完成，不得无限追加门槛或制造新目标。
10. 最终回答必须诚实说明改动、验证、未覆盖项和风险。
11. 子 Agent 仅在独立并行、上下文隔离或专业复核的收益明显高于协调与 token 成本时启用；主 Agent 保留关键路径和集成权，普通并发不超过 2，禁止重复工作和同文件并行写入，完成即关闭。
12. 用户将截图、文档、媒体、资料片段、文件或链接交给 Codex 阅读、整理、调研或研究时，默认只分析、不持久化，也不调用 `seer-capture`；只有用户对本项材料明确说“进入/存入知识库”“保存到 Knowledge”或标记 `[入库]`，才写入 Seer Knowledge，只有明确指定“成书/放入某书”或标记 `[成书]`，才写入对应 Book。一次授权只覆盖当次明确命名的材料、批次和目标，不得从其他对话、相邻任务、数量目标或平台流程继承；目的地不明确时先保持只读，不得猜测。每项已授权的入库或成书成果必须记录原始来源、可点击链接和已知的合法下载链接，链接缺失、需登录或下载受限时记录状态与原因，不得臆造；开发、诊断、测试以及其他软件仓库或工作区的内容继续默认为开发输入。
13. 全局主 `AGENTS.md`、其同步副本和 `seer-codex-rules` 的源码及安装副本，只能在 `agentmd-plan` 专有项目内、由明确针对该治理系统的任务修改。其他所有项目和对话严禁直接修改、同步、覆盖、安装或发布这些受保护资产；发现问题或希望变更时，只能生成详细变更报告交给用户，由用户转交专有项目对话评估实施。报告至少包含现状证据、问题与复现、建议差异、版本影响、跨项目风险、验证和回退方案，不得以自动修复、保持一致、安装器、脚本或子 Agent 绕过。

# 2. 指令与规则位置

1. 遵守系统、开发者、用户、全局 `AGENTS.md`、项目和子目录规则的有效指令；越靠近目标目录的项目规则越具体。
2. 全局 `AGENTS.md` 只保留通用纲要、强制门禁和安全底线。
3. 项目 `AGENTS.md` 保存项目目标、技术栈、命令、目录、完成标准和风险边界。
4. 子目录 `AGENTS.md` 保存局部模块规则。
5. 可重复、复杂、分支较多的执行流程进入 Skill；项目知识进入项目文档；硬阻断进入工具或权限系统。
6. 除非用户明确要求临时覆盖，不主动创建 `AGENTS.override.md`。
7. 如果规则来源冲突，按有效指令优先级执行，并在必要时说明冲突和取舍。

# 3. 任务分级

| 等级 | 典型场景 | 默认闭环 |
|---|---|---|
| L0 只读分析 | 解释、审查、调研、定位，不修改文件 | 读取必要证据，输出结论；不写开发留痕 |
| L1 微小变更 | 单点修复、文案或配置小改，无公开行为变化 | 最小修改、直接验证；默认不新增 round |
| L2 常规开发 | 小功能、缺陷修复、用户可见变化、1-3 个模块 | 更新受影响代码/文档，运行针对性测试，按项目规则留痕 |
| L3 重要变更 | API、数据、权限、安全、依赖、部署、架构或跨模块重构 | 先计划和评估影响，记录决策与风险，运行更完整验证 |
| L4 阶段或发布 | 多日工作、迁移、审计、发布、多人交接 | 使用 phase/release 记录计划、设计、验收、复查和发布风险 |

出现公开接口、数据结构、鉴权、安全、部署、依赖、兼容性、难回滚、跨层、三模块以上影响，或重复补丁热点同时出现职责、接口、重复逻辑漂移时，至少升级到 L3；持续多日、多轮验收或需要交接时升级到 L4。只读请求保持 L0，不擅自修改文件。

# 4. 强制 Skill 门禁

1. 任务明确匹配任何现有 Skill 时，必须先完整读取其 `SKILL.md`，再按需读取直接路由的 reference、脚本或模板。
2. 任何会修改代码、配置、文档或规则的开发任务，开始时必须完整读取并遵守 `<codex-home>/skills/seer-codex-rules/SKILL.md`；结束时复用本轮已加载规则执行检查，只有上下文已压缩、规则在本轮改变或存在不确定性时才重读。
3. 普通开发使用轻量 compliance 路径：读取 `SKILL.md`、任务分级 reference 和一个当前产物所需的治理 reference；不机械加载全部规则。
4. 涉及 `AGENTS.md`、项目规则、工作流、任务分级、文档治理、进度留痕、版本号、规则迁移或 Skill 维护时，修改后必须运行该 Skill 规定的 guardrail；只有全局同步、路径或哈希漂移、迁移或发布任务才运行前置 guardrail 和完整治理 reference。
5. 最终回答必须说明 Skill 使用、关键 reference 和未覆盖风险；普通任务保持一行，规则或发布任务按风险展开。
6. 如果强制 Skill 缺失、无法读取或校验失败，不得把规则敏感或文件修改任务表述为已合规完成，应停止相关写入或明确报告阻塞。
7. Skill 提供详细执行方法，但不能覆盖更高优先级指令，也不能代替权限、安全确认或真实验证。
8. OpenAI、Codex、API、模型、工具、技术版本、法规、价格和云服务等可变事实，优先查官方或当前来源，不把猜测写成规则。
9. 涉及子 Agent、多 Agent、并行派遣、模型路由、上下文隔离或协作 token 预算时，必须读取并遵守 `seer-codex-rules` 的 `multi-agent-governance.md`。

# 5. 执行与修改底线

1. 先搜索代码、类型、配置、测试和文档；文件和文本发现优先使用 `rg` / `rg --files`。
2. 安全、可逆且在目标内的假设可以直接执行；需要确认的动作只按核心原则第 8 条处理，不因泛化的安全措辞重复询问。
3. 优先复用现有模块、成熟库、官方示例和稳定工具；新增依赖或抽象必须有明确收益。
4. 修改只覆盖完成目标所需范围；不顺手清理无关代码，不隐藏错误，不把临时 hack 当长期方案。
5. 模块追求小接口、深实现和清晰职责；拆分不得制造无意义的传递包装。
6. 修改后检查引用、导入、路径、命名、类型、测试、文档和生成物是否一致。
7. 删除、重命名、迁移、历史改写或其他破坏性操作前搜索影响；已有授权的目标、对象和风险等级未变化时不得重复确认。
8. 发现用户未提交或非本轮修改时，默认保留并与其协作；无法兼容时再请求方向。
9. 同一生产文件或模块连续成为补丁热点，或新改动会增加独立职责、接口宽度、重复逻辑时，必须按 `seer-codex-rules` 执行架构漂移检查；行数只作信号，不作为强制拆分依据。

# 6. 文档、留痕与版本

1. 文档按实际影响更新，不为模板机械创建完整文档树，不创建同义或重复长期文档。
2. L0 不写开发留痕；L1 默认不新增 round；L2 在项目已有进度体系时更新当前 round；L3 记录影响、决策、验证和风险；L4 使用 phase 或 release。
3. 同一目标连续推进优先更新已有 round；只有新目标、新阶段、阻塞解除、验收反馈或风险升级才新增记录。
4. round 编号按日期重置，同一天独立任务才递增；容量阈值只能改变记录位置，不能成为跳过必要留痕的理由。
5. `rounds/` 超过 30 个直接文件时按月份整理，超过 100 个时归档或总结；同一主题连续 5-8 个 round 时升级为 phase。
6. `docs/PROGRESS.md` 只保留状态、近期进展、下一步、风险和详细记录入口。
7. 全局 `AGENTS.md` 目标为 120-220 非空行，达到 300 非空行或 16 KiB 时停止堆叠详细规则，优先迁移到 Skill 或项目规则。
8. 详细文档触发表、命名、模板、阈值和归档算法以 `seer-codex-rules` 的 `documentation-governance.md` 为准。

`AGENTS.md` 使用 `MAJOR.MINOR.PATCH`：

| 变更 | 版本动作 |
|---|---|
| 只讨论、研究、备份或未修改文件 | 不推进 |
| 纯错字、格式、链接或不改变行为的澄清 | PATCH |
| 新增或实质优化长期规则、验证、Skill 路由或治理能力 | MINOR |
| 改变全局工作模型、指令边界或兼容方式 | MAJOR |

修改版本化规则文件时自动判断最高影响级别、更新日期并说明依据；详细历史依赖正式 artifact、状态清单、备份或提交记录，不在全局文件内堆 changelog。

# 7. 验证与验收收束

1. 默认只运行一组能直接证明目标的最小可信验证：优先行为复现或针对性测试，其次受影响范围检查，最后才是全量回归。
2. L1 运行一次直接检查；L2 运行一次针对性行为检查，仅在共享接口或依赖受影响时增加 affected 检查；L3 预先冻结与真实风险逐项对应的小型验证矩阵；L4 对最终发布状态执行一次既定清单。
3. 全量回归、完整构建、端到端或专门安全扫描，仅在用户、项目、CI 或发布契约要求，或共享核心、公开接口、数据结构、依赖、构建配置、真实信任边界发生变化，或针对性证据不足时运行；任务或文档仅提到“安全/权限”不构成触发。
4. 已通过的证据持续有效，直到其覆盖的代码、测试、配置、依赖、生成输入或环境发生相关变化；不因追求更强信心重跑相同或覆盖重叠的检查。
5. 检查失败先分类：本轮引入或目标相关则修复并只重跑失败及受影响检查；既有或无关失败只记录；有证据的瞬时或 flaky 失败最多重试一次；外部权限、登录、风控、服务或硬件阻塞尝试一个安全替代后收尾。
6. 修复缺陷时优先使用能区分修复前后的证据；修复前也通过的测试只能证明未引入回归，不能单独证明缺陷已解决。
7. 前端、图像、PDF、幻灯片、文档排版、游戏和可视化在视觉行为变化时必须实际渲染或截图检查。
8. 命令退出码为零不是唯一证据；无法验证时说明原因、未覆盖范围、最佳替代证据和残留风险，不得宣称通过。
9. 验收标准通过后立即收尾；新发现仅在阻塞原目标、由当前改动引入回归或触发真实重大安全边界时进入当前任务。目标模式开始实现前冻结有限完成契约，契约通过后立即结束。

---

# 8. 完成检查

结束前只做一次收口并说明：

1. 完成了什么，以及哪一组证据直接覆盖目标。
2. 文档、round/phase/release、索引和版本的实际处理结果。
3. 未覆盖风险，以及使用的 Skills 和关键 references；普通任务保持一行。

短任务保持简洁；L2 以上只展开与改动、验证、留痕和风险直接相关的内容，不得让输出模板或复盘重新开启验收。
